### Depth interrogation (Tech, APPLIES)

INVARIANT-ENFORCER: the invariant is "the plugin's `plugins_loaded` bootstrap chain never throws an uncaught fatal." Enforcer: this CI job alone (`boot-test.yml` → `bin/boot-test.php`, non-zero exit on uncaught Error/Exception). Fail direction: **fails OPEN** — confirmed live, `gh api repos/Bluerails-2-0/bluerails-agent-traffic/branches/main/protection` → `404 Branch not protected`, so nothing stops a direct push to `main` from skipping this check entirely, and the release process (`README.md` "Cutting a release") `rsync`s from the local working tree rather than a pinned git ref CI ever validated. Both gaps are disclosed in the PR body's "What this does NOT close" section and tracked as a named follow-up, not silently dropped — this ticket's own scope is the boot-test itself, not repo-wide enforcement.
PROD-ENTRY-TRACE: N/A — this only runs in GitHub Actions CI; it has no production entry point of its own. Its downstream effect (the bug class it's meant to catch) traces to every WordPress install's very first `plugins_loaded` request after an update, which is real prod impact for a test that FAILS to catch something — but the test itself has no prod runtime.
PARITY-CHECK: the one dual-source pair worth checking is the stub function/constant list vs. what the real bootstrap chain actually calls. Independent reviewer ablated all 23 stubs individually against the real code and found 7 non-load-bearing on the exercised path (defensive, for callback bodies not invoked) — not a parity BUG (removing them doesn't break anything, they're just unnecessary on this path), but the file's comment claiming otherwise was a real inaccuracy, now fixed (see Fix disposition).
FAILURE-MODE-ENUM: (1) a namespace/class typo in the plugin or its update-checker usage → CAUGHT (this is the target bug class, reproduced live). (2) A fatal inside a hook *callback* body (not the `plugins_loaded` registration itself) → NOT caught, by design, and explicitly disclosed in the file's own "WHAT THIS TEST DOES NOT REACH" docblock, independently verified accurate by the reviewer against the real source. (3) A direct push to `main` bypassing PR review entirely → NOT caught (no branch protection, disclosed). (4) A release zip built from an uncommitted/wrong local state → NOT caught (rsync-from-working-tree, disclosed).
SIDE-EFFECT-COMPLETION: N/A — no money/row/message/external-API side effect. The test does stub `wp_remote_post()` to a no-op (confirmed by the reviewer: this means PUC's real GitHub update-check network call never actually happens under this harness) — correctly scoped out, not a completion gap, since a live network round-trip isn't this test's job.
STATE-MACHINE-COMPLETENESS: N/A — no DB schema, no enum, no response-shape change.
IDEMPOTENCY-REPLAY: N/A — no webhook/queue/MCP tool. Running the boot-test twice in a row is trivially idempotent (pure read + define, no persisted state).
